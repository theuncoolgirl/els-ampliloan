# Integration decisions and documentation review
Reviewed 2026-11-11. These are build decisions informed by official documentation, not proof of enabled account capabilities. Recheck installed package types, versions, and project settings when implementing; record versions in SETUP.md. Source links below are the reference set for Cursor.

## Amplitude
1. Use only `@amplitude/unified`. Create one initialization promise per page load; do not initialize in route components or repeat on React development re-renders. Await `initAll` directly, unlike the `.promise` pattern used by many analytics methods. No second script loader or standalone Analytics initialization. Unified includes Experiment but does not fetch flags on initialization; leave it unused. Verify no Experiment network activity or calls in final QA. [Unified overview](https://amplitude.com/docs/sdks/analytics/browser/browser-unified-sdk/get-started) · [reference](https://amplitude.com/docs/sdks/analytics/browser/browser-unified-sdk/reference)
2. Resolve actual project region; configure the unified serverZone consistently. Set the app-owned browser ID as Amplitude deviceId using the supported installed API before the first business event. On mock login, set the shared known userId and identify traits before tracking dependent events. First-touch traits use setOnce; mutable lifecycle traits use set. These updates do not rewrite historical events. [Browser configuration](https://amplitude.com/docs/sdks/analytics/browser/browser-sdk-2/instrument-and-configure) · [Identify](https://amplitude.com/docs/sdks/analytics/browser/browser-sdk-2/identify-users)
3. Preserve landing query attribution before hash navigation. Use built-in acquisition tracking; don't install a separate legacy marketing SDK. Keep vendor-native attribution and a small explicit cross-platform contract. No full URLs with uncontrolled query values in custom properties. Strip fragments/query from custom paths and allowlist campaign tags. [Marketing attribution](https://amplitude.com/docs/sdks/analytics/browser/browser-sdk-2/marketing-analytics)
4. Replay requires project capability and a nonzero sample rate. For synthetic live demos propose 1, explicitly configured; inspect actual masking and playback. Never infer replay success from event arrival. Autocaptured page/click events are separate from the 17 curated business events; do not implement duplicate business events via autocapture. [Replay](https://amplitude.com/docs/session-replay/session-replay-integration) · [Unified reference](https://amplitude.com/docs/sdks/analytics/browser/browser-unified-sdk/reference)
5. Guides/Surveys SDK presence does not publish content. Set allowed origins, target stable data-demo anchors and documented profile values, and separately verify actual display/response. Prefer current scalar traits for immediate demo targeting; behavioral cohorts may take time to update. Draft guide, friction survey, and resource center require console configuration/entitlement and explicit publication authorization. [SDK](https://amplitude.com/docs/sdks/guides-and-surveys/sdk) · [Targeting](https://amplitude.com/docs/guides-and-surveys/setup-and-target)
6. Heatmaps are conditional on enablement and sufficient captured interaction, not a reason to manufacture extra application routes. Record available/unavailable and evidence. [Heatmaps](https://amplitude.com/docs/heatmaps/create-a-heatmap)

## Statsig
1. Use `@statsig/js-client`; optional compatible React bindings only when needed. Omit Statsig replay/autocapture packages because this project uses Amplitude for those capabilities and an explicit business-event adapter. Client key may be public; management/server secret keys may not. Use one client with typed defaults and an explicit environment tier. [JS SDK](https://docs.statsig.com/client/javascript-sdk) · [React](https://docs.statsig.com/client/React)
2. Put segmentation traits in `custom`, a known mock identity in `userID`, and the app-owned browser identifier in `customIDs.stableID` using the supported API. Do not put desired analysis dimensions in privateAttributes: those are not retained for analytics. Build the entire user object from one profile and await updateUserAsync before evaluating a dependent feature. [User object](https://docs.statsig.com/sdks/user) · [JS SDK](https://docs.statsig.com/client/javascript-sdk)
3. Proposed main experiment unit is Stable ID, retained across anonymous-to-known transition in one browser. Configure metrics with that same unit. Before activation verify an actual exposure and outcome carry the intended stable ID. No cross-device identity guarantee. Results breakdowns can use baseline properties captured at exposure, so active_loan_type changes later must not be interpreted as historical exposure context. [User-property breakdowns](https://docs.statsig.com/experiments/interpreting-results/user-properties)
4. Page components request typed parameters through an integration facade. Parameter stores decouple app code from the backing entity. Use four stores mapped to four page layers, as proposed separately. Read only the parameter actually used at render/action time. Layer parameter access can log exposure; don't pre-read every page or evaluate again for diagnostics. Record snapshots of already evaluated values for the presenter. [Parameter stores](https://docs.statsig.com/client/concepts/parameter-stores) · [Layers](https://docs.statsig.com/experiments/layers-overview)
5. Choose the layer before starting an experiment; mutually exclusive experiments in one layer differ from experiments in separate layers. Initial walkthrough activates at most one application-layer experiment, so other page changes cannot confound its story. Draft creation and activation are different authorizations. [Layers](https://docs.statsig.com/experiments/layers-overview)
6. Send the same Title Case custom event name, numeric value only for its defined measure, and flat string metadata. Serialize booleans as true/false and numbers as canonical decimal strings; Amplitude preserves original types. Avoid custom property blobs and do not assume business_event_id causes Statsig server deduplication. Verify accepted payloads against installed SDK typings. [Custom events / SDK](https://docs.statsig.com/client/javascript-sdk)
7. An exposure-based conversion metric and a daily user funnel are different analyses. Final console recipe must name unit, eligible exposure, traffic filter, attribution window, aggregation, and timezone; reconcile rather than promising equality with Amplitude. [Statsig funnels](https://docs.statsig.com/metrics/create-user-funnels)

## Application architecture and failure behavior (project decisions)
- Suggested boundaries: src/state/application.ts (transitions), src/identity/profile.ts (single profile), src/telemetry/events.ts (typed contract), src/telemetry/dispatch.ts (one business emitter), src/integrations/amplitude.ts, src/integrations/statsig.ts, src/integrations/pageParameters.ts, src/presenter/** (diagnostics). Only adapters call vendor APIs.
- Resolve identity and configuration before enabling live telemetry. Allow at most 2000ms UI wait for initialization; render safe local defaults afterward. Late completion must not switch a visible application variant mid-step. Retry evaluation at a safe route boundary. Ignore stale asynchronous responses using profile-generation tokens. Never reuse another identity's cached values.
- Disabled/missing-key mode is visibly local, with zero vendor sends. Preview overrides use a local resolver before any SDK reads and suppress business-event sends; do not call Statsig to obtain an overridden value. Live demo uses actual evaluation. Synthetic population requires a separately approved bounded recipe.
- Login retains stable ID and sets known identity in both tools. Sign Up Completed means a local synthetic profile was created; Signed In means returning fixture selected. Neither is authentication. Signed Out is logged under old identity before both adapters clear it, then rotate browser stable ID and clear active application context. New-user reset also clears all local profile/application/attribution state. Application reset creates a new application ID while retaining identity and attribution. Expose these different actions clearly.
- Keep loan_type immutable after Application Started; changing type starts a new application with confirmation. Multiple applications can belong to one demo user. Historical event loan_type is authoritative; mutable active_loan_type supports current targeting.
- Persist submission state before dispatch, disable repeated submit, and use one immutable business event ID/insert_id. No automatic custom retry across reload; vendor SDK retry behavior is separate. Document that browser failures can lose telemetry and exact-once remote delivery is not guaranteed. Don't fabricate recovery events or unload abandonment.
- Static hosting cannot protect a secret or enforce real lending/auth rules. Use synthetic values only. Configure hash routing with verified Vite base. [Vite deployment](https://vite.dev/guide/static-deploy.html)

## Scope boundary
No backend/server SDK, warehouse-native setup, Amplitude Experiment configuration, production data, real credit decisions, uploads or revenue. SDK loading, configured console assets, real receipt, and sufficient data for analysis are distinct readiness levels. A scripted demo is not evidence of causal lift or statistical significance.
